# api-php — Laravel v0

The v1 reservation path, rewritten in Laravel, to measure what the language and
the framework cost. **Nothing else is allowed to differ.** If any row below were
not identical, the comparison with v1 would measure that row instead.

| | Go `v1` | Laravel `v0` / `v0b` |
|---|---|---|
| Database | the compose `postgres` container | the same container |
| Schema | `internal/flashsale/schema.sql`, applied at startup | the same file, mounted read-only, under the same advisory lock — no Laravel migration |
| Transaction | BEGIN, replay check, conditional UPDATE, replay + limit check, INSERT, COMMIT | the same six round trips, verified in the Postgres statement log |
| SQL | `postgres.go` | the same statements; `?` placeholders instead of `$n`, because PDO only parses `?` |
| Idempotency | `UNIQUE (sku, request_id)`, per SKU | the same constraint |
| Per-user limit | `products.per_user_limit`, written at seed time from `PER_USER_LIMIT` | the same column, the same variable |
| HTTP contract | `internal/httpapi/router.go` | the same paths, headers, bodies, status codes and error strings |
| Connections | pgxpool, `DB_MAX_CONNS=25` | 25 FPM workers, one persistent connection each |
| Load test | `k6/` | the same scripts; only `BASE_URL` changes |

## Two backends

- **`v0` — `RawReserver`**: `DB::selectOne()` and friends, no models. The gap to
  v1 is Laravel and PHP-FPM.
- **`v0b` — `EloquentReserver`**: the same transaction through `Product` and
  `Order` models. The gap to v0 is the ORM: query building, hydration, casts and
  model events.

v0b keeps v0's round trips on purpose. Eloquent cannot express
`UPDATE … RETURNING`, and the idiomatic substitute — `decrement()` and then read the
row back — adds a round trip *while the row lock is held*. That would measure a
longer critical section, not the ORM, so the decrement is raw SQL hydrated through
`Product::fromQuery()`. Every other statement is generated by the query builder.

Both are complete Laravel 13 — `laravel/framework`, its default global middleware
stack, routing, the container, facades, exception handling. Not Lumen, not a
micro-framework. Measuring a stripped-down Laravel would avoid the question.

## Verifying the alignment

**HTTP.** 25 requests — every status the reservation can return, every
validation error, an over-size body, an unknown version, the stock endpoint — were
sent to v1, v0 and v0b in turn, and the responses diffed after replacing the
`backend` field. Status codes, bodies and the echoed `X-Request-Id` header are
byte-identical across all three, including the key order Go produces when it
encodes a map.

**SQL.** With `log_statement = all`, one successful reservation on each backend
produces:

```
v1    begin · SELECT EXISTS … · UPDATE … RETURNING · SELECT EXISTS …, SUM … · INSERT · commit
v0    BEGIN · SELECT EXISTS … · UPDATE … RETURNING · SELECT EXISTS …, SUM … · INSERT · COMMIT
v0b   BEGIN · select exists(…) · UPDATE … RETURNING · select EXISTS …, SUM … · insert … returning "id" · COMMIT
```

Six round trips each, no `SET`, no extra statement. One difference remains and is
inherent: pgx binds a statement it prepared once per connection, while PDO sends an
unnamed Parse with every execution, so Postgres re-plans each statement for PHP. In
the same trace that costs 0.03–0.2 ms of server time per statement, and it is part
of what "the PHP driver" means.

**Behaviour.** `k6/correctness.js` runs the Go suite's exact-count assertions over
HTTP: stock 100 and 1,000 concurrent buyers yield exactly 100 reservations and 900
sold-outs, 200 concurrent replays of one `request_id` take exactly one unit, and
one user's 20 concurrent attempts take exactly `PER_USER_LIMIT`. v0 and v0b pass,
as do v1, v2 and v3 (`make correctness`). The same script given a wrong
`PER_USER_LIMIT` fails, so the thresholds are not vacuous.

## Tuning — everything a production Laravel deployment would turn on

Leaving any of this off would make Laravel lose for reasons that have nothing to do
with Laravel, and a reader would be right to discount the result.

| Setting | Value | Where |
|---|---|---|
| Process manager | `pm = static`, no worker forked mid-run | `php-fpm.conf` |
| Workers | `pm.max_children = 25` (`FPM_WORKERS`, defaults to `DB_MAX_CONNS`) | `php-fpm.conf`, compose |
| Worker recycling | `pm.max_requests = 0` | `php-fpm.conf` |
| OPcache | `opcache.enable = 1` | `opcache.ini` |
| Timestamp checks | `opcache.validate_timestamps = 0` | `opcache.ini` |
| JIT | `opcache.jit = tracing`, 64 MB buffer | `opcache.ini` |
| Environment | `APP_ENV=production`, `APP_DEBUG=false` | `Dockerfile` |
| Framework caches | `php artisan optimize` — config, routes, events, views | `docker-entrypoint.sh` |
| Autoloader | `composer dump-autoload --classmap-authoritative` | `Dockerfile` |
| DB connections | `PDO::ATTR_PERSISTENT` — reused across requests | `config/database.php` |
| Statement mode | `Pdo\Pgsql::ATTR_DISABLE_PREPARES` — one round trip per statement | `config/database.php` |
| nginx → FPM | unix socket, `listen.backlog = 4096`, `somaxconn = 4096` | `php-fpm.conf`, compose |
| nginx keep-alive | `keepalive_requests 1000000`, as Go never closes a busy connection | `nginx.conf` |
| Logging | no access log, errors to stderr | `nginx.conf`, `LOG_CHANNEL` |

`config:cache` runs at container start rather than build time because it bakes the
environment into the cache, and `DATABASE_URL` only exists once compose has started
the container.

### Why 25 workers

A worker is a process that handles one request at a time and holds one persistent
connection, so the worker count *is* PHP's connection pool. Setting it to
`DB_MAX_CONNS` gives both servers the same 25 connections to Postgres, which is the
resource the row lock serialises on.

The usual sizing rule — container memory ÷ per-worker RSS — is not the constraint
here. Under load each worker is 31–38 MiB RSS (shared pages included) and the whole
container is 160 MiB by cgroup accounting, so a 2 GiB container would allow 50.
**50 was measured and is worse**: 500/s sustainable against 600/s with 25, because
more concurrent transactions only add waiters on the same row lock. The worker count
is not starving Laravel.

### The two settings that are not Laravel's defaults

Persistent connections and disabled prepares are the only places this deviates
from what `laravel new` produces, and both exist to keep the round-trip count equal
to v1's. Out of the box, each request opens a new Postgres connection — TCP, SCRAM
authentication, a forked backend — and each statement is a named prepare followed
by a separate execute. Measured with both defaults restored, v0 sustains **200/s**
instead of 600/s and its unloaded median goes from 3.7 ms to 13–14 ms. Without the
two settings, this would be a benchmark of Postgres connection setup.

## Results

Measured 2026-10-01 alongside v1, same session, alternating runs. Full tables and
method in [`docs/benchmarks.md`](../docs/benchmarks.md#laravel-v0--2026-10-01).

| | v1 Go | v0 Laravel | v0b Eloquent |
|---|---|---|---|
| Sustainable rate (ramp) | 800/s | **600/s** (75%) | **400/s** (50%) |
| Peak achieved | 835/s | 626/s | 480/s |
| 50 VUs × 30 s | 661–703 req/s | 526–540 req/s | 409–414 req/s |
| Unloaded p50 | 1.43 ms | 3.69 ms | 4.98 ms |
| Exact-count correctness | pass | pass | pass |

The knee is the row lock, as for v1: neither server is CPU-bound, and Laravel's
cost lands on throughput only through the ~0.4 ms it spends between statements
while the row is locked. Eloquent adds ~0.5 ms more inside the same window and
costs a third of v0's sustainable rate.

## Limitations

- **One container runs nginx and PHP-FPM.** That is the common deployment shape;
  the entrypoint exits if either process dies, rather than leaving nginx answering
  502 in front of a dead pool.
- **No `/metrics`.** Prometheus does not scrape this service, so the Grafana
  dashboard shows nothing for v0. k6's own summary is the measurement.
- **No OPcache preload.** It would shave the class-loading part of bootstrap;
  with `validate_timestamps = 0` and a warm cache that part is already small.
- **No Octane.** FPM bootstraps the framework on every request, which is how most
  Laravel runs in production and is the cost this version exists to measure. An
  Octane + Redis Lua variant (v0.5) would ask a different question — whether the
  language matters once the architecture is fixed — and is not built yet.

## Running it

```bash
make up                     # api-php is part of the stack, on :8090
make correctness-v0         # exact-count assertions
make bench-v0               # 50 VUs, 30 s
make ramp VERSION=v0 STEP=100 MAX_VUS=2000
```

The code that matters is three files: `app/FlashSale/RawReserver.php`,
`app/FlashSale/EloquentReserver.php` and `app/Http/Controllers/ReserveController.php`.
